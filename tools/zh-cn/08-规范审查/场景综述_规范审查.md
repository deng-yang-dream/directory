# 场景综述：规范审查

> 文档日期：2026-06-12
> 目的：从设计师、产品、技术三层视角整合规范审查场景的完整认知

## 一、设计师视角：规范查询这件事为什么这么痛苦？

### 建筑师查规范的三大痛点

1. **不知道查哪条**：知道"楼梯宽度应该够大"但不知道 GB 50352《民用建筑设计统一标准》第 6.8.3 条——检索关键词匹配不到
2. **找到条文看不明白**：条文说"高层建筑应设置环形消防车道"，但"什么是高层""环形怎么定义"需要交叉引用其他条文
3. **多条规文冲突不知道听谁的**：国标/行标/地标的同一事项可能有不同要求——需要判断优先级

### 规范查询工具的三种深度

```
Level 1：电子 PDF（免费公开）
  → "搜索关键词 '栏杆高度' 找到条文"

Level 2：AI 自然语言查询（规范问答工具、UpCodes 等）
  → "六层住宅的栏杆要多高？" → AI 检索+返回相关条文+原文定位

Level 3：AI 自动审图（小库, PKPM-AIChecker）
  → 上传 CAD/BIM 模型 → AI 检查全部规范项 → 输出不通过列表
```

目前市场上：
- Level 1 是默认状态（每个建筑师都在用）
- Level 2 有少数产品，国内个人可用的规范问答产品仍较少
- Level 3 只有企业级产品（小库/PKPM/TransBIM）

### 个人建筑师 vs 设计院的差异

| 需求 | 个人建筑师 | 设计院 |
|---|---|---|
| 查询频率 | 偶尔（方案提交前查关键项） | 日常（所有项目需要合规） |
| 查询深度 | Level 2 够用 | Level 3 是刚需 |
| 付费意愿 | 低（规范是公开信息） | 中高（合规是红线） |
| 核心痛点 | 不知道查哪条 | 逐条人工检查太慢 |

## 二、产品视角：规范审查赛道产品分析

### 规范审查赛道竞争格局

| 工具 | 等级 | 中国市场 | 个人可用 | 规范覆盖 |
|---|---|---|---|---|
| PKPM-AIChecker | L3（自动审图） | ✅ | ❌（企业） | 结构规范为主 |
| 小库设计云 | L3（实时校核） | ✅ | ❌（企业） | 规划规范为主 |
| TransBIM | L3（施工图校核） | ✅ | ❌（企业） | 全专业 |
| UpCodes | L2（对话查询） | ❌（仅美国规范） | ✅ | 美国规范 |
| 神州数码AI-BIM | L3（自动校验） | ✅ | ❌（企业） | 待验证 |
| 规范问答工具 | L2（对话查询） | ✅/⚠️ | ✅/⚠️ | 视产品而定 |

### L2 规范问答工具的定位

L2 规范问答工具适合个人建筑师或学生在方案阶段快速定位条文、理解概念和确认关键指标，但不能替代正式审图或设计院内部合规流程。

这类产品的主要边界包括：
- **优势**：自然语言提问、条文检索、原文定位，降低查规范门槛
- **局限**：自动审图、地方规范覆盖和跨专业校核通常不足
- **风险**：规范是公开信息，纯查询产品需要通过准确性、覆盖范围和溯源能力证明价值

### L2 到 L3 之间的覆盖空白

1. **地方规范覆盖**：国标之外，北上广深等地方规范仍是高频需求。
2. **半自动校核**："输入关键指标→AI 对照规范判断合规性"介于纯查询和全自动审图之间，可能更适合个人和小团队。

## 三、技术视角：从关键词匹配到条文推理

### 规范审查的技术进化

```
Gen 1：关键词全文检索（Elasticsearch 搜 PDF）
  → 输入"栏杆" → 返回包含"栏杆"的条文

Gen 2：RAG 语义检索（LLM + 向量嵌入 + 条文溯源）
  → 输入"六层住宅栏杆高度" → LLM 理解"住宅+多层+栏板" →
    检索"居住建筑+防护栏杆+高度"相关条文 → 组织回答+标注来源

Gen 3：规则引擎 + AI（条文形式化 + 模型数据提取 + 自动比对）
  → 上传 BIM 模型 → 提取踏步高度/扶手直径/疏散距离等数值 →
    对照数字化规范条文 → 自动判断合规性
```

### 条文的"形式化"是核心技术难点

规范的模糊语言（"应适当加宽""宜采用自然通风""至少不小于 1.1m"）需要转为机器可执行的规则逻辑：
- "应至少" → 数值型硬约束（≥X）
- "宜" → 建议值，可破例
- "适当" → 上下文相关，需要专家判断
