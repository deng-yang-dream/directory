# 效果图工具套壳技术解析

> 文档日期：2026-06-17
> 目的：建立效果图与渲染类工具的“底层模型 / 工作流封装 / 产品能力”判断框架，避免把所有 AI 生图产品都简单归为“自研”或“套壳”

## 1. 先定义：什么是“套壳”

“套壳”在 AI 工具评测里常被当作贬义词，但对效果图工具而言，更准确的说法应是“基于第三方模型或开源工作流的产品封装”。

它本身不一定差。建筑师真正关心的是：这个封装有没有解决建筑工作流问题。

| 类型 | 含义 | 典型形态 | 评价重点 |
|---|---|---|---|
| API 套壳 | 调用 Midjourney、OpenAI、Google、Stability、Replicate、fal.ai 等外部模型 API | Web 生图站、提示词模板站 | 是否只是换皮，还是有建筑场景输入、资产管理、权限和工作流 |
| 开源模型封装 | 基于 SDXL、Flux、ControlNet、ComfyUI、LoRA 等开源生态做产品化 | 本地客户端、云端 ComfyUI、工作流市场 | 节点组合、模型选择、控制链路、部署稳定性 |
| 宿主软件插件封装 | 在 SketchUp、Rhino、Revit、D5、Enscape 等软件中调用云端或本地模型 | 插件、扩展、面板 | 是否真正读取模型视图 / 深度 / 材质，还是只截屏上传 |
| 垂直工作流封装 | 不自研底层模型，但把输入、风格、批量、项目管理、团队协作做成完整流程 | 建筑 AI 渲染平台 | 是否沉淀建筑场景参数和可复用模板 |
| 自研 / 深度微调 | 自建模型、训练建筑 LoRA、微调视觉模型，或训练私有可控生成链路 | 企业级平台、研究型产品 | 数据来源、模型能力、是否可验证 |

因此，工具目录不应只问“是不是套壳”，而应问：

1. 它套的是哪一层？
2. 封装之后新增了什么建筑师价值？
3. 它的关键能力是否可迁移、可复用、可替代？
4. 如果底层模型换掉，产品还能不能成立？

## 2. 效果图工具的五层技术栈

效果图 AI 工具可以拆成五层。很多产品只做了上面两层，但宣传时会把自己说成完整 AI 平台。

```
L5 交付与协作层：项目管理、版本、团队预设、商用授权、导出、权限
L4 建筑工作流层：白模转图、草图转图、风格库、批量、局部修改、插件
L3 控制与编排层：Prompt、ControlNet、Depth、Canny、Lineart、LoRA、节点工作流
L2 模型层：SDXL / Flux / Midjourney / GPT-image / Gemini / Kling / Runway / 自研模型
L1 算力与部署层：本地 GPU、云 GPU、第三方 API、队列、缓存、加速
```

判断一个工具的技术含金量，不能只看 L2，而要看它在 L3-L5 有没有不可替代的积累。

### 2.1 L1 算力与部署层

| 部署方式 | 特征 | 对建筑师的影响 |
|---|---|---|
| 纯第三方 API | 工具本身不控制模型和算力 | 成本、限额、稳定性受上游影响 |
| 自有云 GPU | 平台维护自己的推理队列和模型部署 | 成本较高，但可控性更强 |
| 本地 GPU | 用户机器运行 SD / ComfyUI / Flux | 隐私好、成本低，但门槛高 |
| 混合部署 | 本地插件 + 云端生成 / 云端增强 | 体验平衡，但要关注上传数据 |

### 2.2 L2 模型层

| 模型来源 | 常见能力 | 局限 |
|---|---|---|
| 通用闭源模型 | 语义理解强、画质好、上手简单 | 结构控制弱、不可微调、不可私有化 |
| 开源扩散模型 | 可部署、可控、生态丰富 | 调参复杂，文字和多轮编辑弱 |
| 视频生成模型 | 动态效果强，适合传播 | 建筑结构容易变形，不适合施工级表达 |
| 自研 / 微调模型 | 可针对建筑风格或企业资产优化 | 数据和训练成本高，真实能力需验证 |

### 2.3 L3 控制与编排层

这是效果图工具最关键的技术层。

建筑生图不是“把图画好看”，而是“在不破坏结构的前提下变好看”。因此 L3 的控制链路比底层模型名更重要。

| 控制方式 | 作用 | 建筑场景价值 |
|---|---|---|
| Canny / Lineart | 提取线稿轮廓 | 保持立面、窗洞、边界 |
| Depth | 保持空间深度和透视 | 白模 / 室内 / 景观鸟瞰更稳定 |
| MLSD | 识别长直线 | 建筑立面、室内空间、街景更有用 |
| Segmentation | 区分天空、建筑、道路、植被、水体 | 适合局部替换和景观控制 |
| LoRA / Style model | 固定风格或材料倾向 | 团队风格统一、企业视觉资产复用 |
| IP-Adapter / Reference | 参考图风格或构图迁移 | 保持案例参考和品牌视觉一致 |
| ComfyUI 工作流 | 把多个节点组合成可复用流程 | 形成“建筑师最佳实践模板” |

如果一个工具只提供 prompt 输入，没有任何结构控制，它更适合概念探索；如果它能读取深度、线稿、材质或宿主软件视图，它才有机会进入方案深化。

### 2.4 L4 建筑工作流层

这是区分“普通 AI 生图站”和“建筑工具”的核心。

| 工作流能力 | 普通套壳表现 | 有价值封装表现 |
|---|---|---|
| 白模转图 | 上传截图 + prompt | 自动识别透视、深度、材质区域，保留结构 |
| 草图转图 | 草图作为参考图 | 线稿控制强度可调，可保留设计意图 |
| 风格库 | 预设 prompt | 风格包含材料、气候、地域、建筑类型约束 |
| 局部修改 | 整张重画 | 只改天空、立面材料、植物、灯光 |
| 批量生成 | 一次 4 张随机图 | 可批量跑风格、视角、季节、时间段 |
| 插件支持 | 插件只是截屏上传 | 读取模型相机、图层、材质、深度或对象信息 |
| 输出衔接 | 下载 JPG | 能进入 PS/PPT/模型软件/团队素材库 |

### 2.5 L5 交付与协作层

很多产品虽然底层模型普通，但如果 L5 做得好，仍然有产品价值。

| 能力 | 为什么重要 |
|---|---|
| 项目式保存 | 建筑方案不是一次性生图，需要按项目追踪版本 |
| Prompt / 参数复用 | 设计团队需要复用成功经验，而不是每次重新试错 |
| 团队预设 | 保持事务所或课程组的视觉风格一致 |
| 权限与素材管理 | 防止客户项目资料散落在个人账号 |
| 商用授权说明 | 决定能否用于投标、汇报、公众号、作品集 |
| 导出规格 | 影响是否能进入展板、PPT、印刷和视频流程 |

## 3. “套壳”不是一个等级，而是一张光谱

建议把效果图工具按技术深度分为 5 级，而不是二分为“套壳 / 自研”。

| 等级 | 名称 | 判断标准 | 代表形态 | 评测口径 |
|---|---|---|---|---|
| T0 | 简单 API 换皮 | 只调用第三方模型，主要卖 prompt 模板或积分差价 | 通用生图小站 | 谨慎收录，除非有明显场景价值 |
| T1 | 场景模板封装 | 有建筑 / 室内 / 景观模板，但控制能力弱 | Web 生图工具 | 看模板质量、价格、导出和免费额度 |
| T2 | 可控工作流封装 | 使用 ControlNet、Depth、LoRA、ComfyUI 等形成稳定流程 | 云端 SD / ComfyUI 平台 | 看结构保持、批量和失败率 |
| T3 | 宿主软件深度集成 | 与 SU/Rhino/Revit/D5 等软件连接，能利用模型视图信息 | 插件型工具 | 看是否真读取模型数据，而非截图上传 |
| T4 | 垂直模型 / 数据积累 | 有建筑数据、专属模型、企业风格库或私有化能力 | 企业级或专业平台 | 看数据来源、可验证案例和部署能力 |

对工具目录来说，T1-T3 都值得评测。T0 价值较低，T4 需要更高验证标准。

## 4. 如何识别一个效果图工具是不是“浅套壳”

### 4.1 产品页面信号

| 信号 | 可能含义 | 可信度 |
|---|---|---|
| 页面只展示“输入 prompt → 出图” | 可能是通用模型 API 封装 | 中 |
| 无模型、无控制、无插件、无工作流说明 | 技术深度可能较浅 | 中 |
| 生成结果风格高度像 Midjourney / SD 社区模型 | 可能调用或复刻通用模型路线 | 低到中，需实测 |
| 价格按“积分 / 张”计费且无自有基础设施说明 | 可能依赖第三方 API 成本转售 | 中 |
| 失败提示、队列名、参数名暴露上游平台特征 | 可能直接接入第三方推理服务 | 高，但需截图证据 |
| 服务条款提到第三方 AI service providers | 可能使用外部模型或云服务 | 高 |

### 4.2 功能测试信号

| 测试 | 浅封装常见表现 | 深封装常见表现 |
|---|---|---|
| 白模转图 | 体块、层数、窗洞随机改变 | 结构基本保留，可调控制强度 |
| 局部修改 | 改天空时建筑一起变 | 局部 mask 或区域编辑稳定 |
| 重复生成 | 同 prompt 结果漂移很大 | 可通过 seed / preset / style 保持一致 |
| 上传线稿 | 把线稿当参考图而非结构约束 | 能明确锁定轮廓、线条和透视 |
| 风格库 | 只是 prompt 词包 | 风格包含参数、模型、参考图和后处理链路 |
| 插件导入 | 插件内截图后跳网页 | 插件能保留相机、材质、图层或对象信息 |

### 4.3 技术文档信号

优先查看以下页面：

1. Terms / Privacy：是否披露第三方 AI 服务、数据使用、训练权利；
2. API / Developer Docs：是否有自有 API，还是只作为前端工具；
3. Plugin Docs：是否说明支持哪些宿主软件版本、读取哪些模型信息；
4. Pricing：是否按积分、算力、训练、放大、视频分别收费；
5. Changelog：是否有持续模型更新、控制能力更新、插件更新。

## 5. 效果图工具的典型封装路线

### 路线 A：通用模型 API + 建筑 prompt 模板

```
用户输入 → 建筑 prompt 扩写 → 第三方图像 API → 返回图片 → 下载
```

优点：上线快、成本低、体验简单。  
缺点：结构控制弱、差异化低、上游模型变化会影响质量。

适合：概念氛围图、灵感图、社媒图。  
不适合：白模深化、投标级稳定图、团队批量交付。

### 路线 B：Stable Diffusion / Flux + ControlNet 工作流

```
白模 / 草图 → 线稿 / 深度提取 → ControlNet / LoRA / 风格模型 → 后处理放大 → 输出
```

优点：结构控制强、可私有化、可形成模板。  
缺点：节点复杂、维护成本高、对 GPU 和调参要求高。

适合：白模转图、风格一致、团队预设、批量生产。  
不适合：零基础用户立即上手。

### 路线 C：宿主软件插件 + 云端生成

```
SU/Rhino/Revit/D5 视图 → 插件采集视角 / 材质 / 深度 → 云端生成 → 回写结果
```

优点：更贴近建筑师工作流，减少导入导出。  
缺点：要看插件是否真读取模型信息，还是只截屏。

适合：日常建模过程中的快速效果图。  
不适合：没有宿主软件基础的轻量用户。

### 路线 D：后期增强模型 + 图像资产工作流

```
已有效果图 → 放大 / 补细节 / relight / 局部修复 → 展板 / PPT / 社媒输出
```

优点：容易嵌入现有渲染流程，价值明确。  
缺点：可能改写材料、文字、logo、栏杆、分缝等事实细节。

适合：展板级增强、封面图、低清图修复。  
不适合：需要严格保真细节的施工或报批材料。

### 路线 E：图生视频模型 + 运镜模板

```
静态效果图 → 图生视频模型 → 运镜 / 动态延展 → 5-10 秒汇报短片
```

优点：传播效果强，适合汇报和社媒。  
缺点：建筑立面和结构容易漂移。

适合：方案展示片、社媒短视频、路演素材。  
不适合：替代真实漫游动画、施工模拟、精确空间表达。

### 7.1 对第二轮调研的总体判断

1. **插件型工具的含金量差异最大**：Veras、D5 Render AI、LookX 的关键不在“用了哪个模型”，而在是否能读取宿主软件的几何、材质、相机、深度或元数据。
2. **视频工具的数据条款差异明显**：Runway、Kling、Pika 都是图生视频候选，但用户内容训练、商用、水印、API 数据处理条款差异很大，不能只比画面效果。
3. **Krea 更像模型聚合器 + 创意工作台**：它的价值在把多种模型统一成实时生成、增强、视频和 LoRA 工作流，而不是单一建筑垂直模型。
4. **Topaz 的差异点不是生成，而是本地增强和默认不训练用户图**：适合放在“后期增强 / 保真放大”而非“白模转图”。
5. **mnml.ai 的 ArchDiffusion 需要重点核验**：如果其自研建筑模型和 no-training 条款属实，技术深度明显高于普通 prompt 模板站。

## 8. 评测时如何写“套壳”判断

不建议在公开评测中直接写“这是套壳，所以不行”。推荐使用更可验证的表达。

| 不推荐写法 | 推荐写法 |
|---|---|
| 这是套壳产品 | 公开资料未显示其自研底层模型，更像基于第三方模型 / 工作流的产品封装 |
| 没技术含量 | 技术差异主要体现在模板、交互和工作流层，底层模型差异尚未看到公开证据 |
| 只是调用 API | 其核心生成能力可能依赖外部模型服务，需关注上游价格、限额和稳定性 |
| 比不上自研模型 | 是否自研不直接决定可用性，关键看结构控制、工作流衔接和交付稳定性 |
| 假 AI | 更准确地说，它是 AI 能力的应用层封装，而非底层模型提供方 |

### 推荐结论模板

> 从公开资料看，该工具的核心价值不在自研底层模型，而在将图像生成能力封装为建筑 / 室内 / 景观工作流。评测重点应放在结构控制、输入输出衔接、版本管理和商用权限，而不是只比较模型名称。

> 该工具目前未公开说明底层模型来源，暂按“第三方模型或开源工作流封装”处理。若后续能证明其具备自研模型、专属训练数据或宿主软件深度读取能力，可上调技术深度判断。

## 8. 技术深度评分建议

可在内部评分中增加“技术透明度 / 封装深度”维度，但不建议直接作为公开星级的唯一依据。

| 评分项 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 模型透明度 | 不说明模型来源 | 说明部分模型或服务商 | 清楚说明模型、版本、更新机制 |
| 结构控制 | 仅 prompt | 支持参考图 / 线稿 | 支持深度、线稿、分割、控制强度 |
| 工作流封装 | 单次生图 | 有模板和历史 | 有项目、批量、预设、团队协作 |
| 宿主集成 | 无 | 截图 / 导入导出 | 读取模型视图、材质、相机或对象信息 |
| 可替代性 | 换个 API 就能复制 | 有一定模板积累 | 有数据、插件、私有化或团队资产壁垒 |
